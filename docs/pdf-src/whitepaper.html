Technical reference

1. Executive summary

Campus is a single-school operations platform — registration, scheduling, attendance, grades and report cards, billing with optional online payments, communication, booking, IEPs and a parent/student portal — that runs entirely on a school's own server, with nothing sent to a third-party cloud by default. Campus Central is a second, separate product built on top of it: a Ministry or district head-office console that any number of individual Campus installs can optionally link to, giving a head office cross-school search, aggregate dashboards (including a district-level illness/health metric) and on-demand case-file detail, without ever holding a school's full, unfiltered database.

The two products are deliberately kept apart rather than merged into one "multi-tenant" system: a school's own Campus install is exactly as self-contained and private as it has always been, whether or not any Ministry ever links to it. Central is opt-in, read-mostly, and receives only a curated, field-limited export — never a school's raw database.

This is the first whitepaper written for this product family. Campus itself has shipped an Overview & User Guide and a Technical & Troubleshooting Guide since September 2026; Campus Central, built across early-to-mid October 2026, had no dedicated product document at all until this one. Every figure in this paper was checked against the actual repository and, where it is a test count, by actually running the test suite — not carried forward from an earlier draft.

2. What Campus is

A single authenticated web console plus a restricted parent/student portal, for a daycare through secondary school to run day-to-day operations. One role per login (superadmin, admin, front desk, teacher/tutor, parent/guardian, student), each seeing only the sections and records their role permits. Built on Django 5.2 (REST API) and a Next.js static-export console, both frozen into one Windows installer with a bundled PostgreSQL database and a bundled Caddy reverse proxy for local HTTPS — no separate Python or Node runtime on the target machine, no Docker in production.

3. What Campus Central is

A Ministry/district head-office product, sold and installed separately from Campus itself (Campus-Central-Setup.exe, its own PyInstaller freeze, its own Next.js console on its own port, its own PostgreSQL database on its own port). A head office registers each participating school, which then links to Central from its own install (a companion window, not a web form) and begins sending it a curated snapshot on a schedule plus on demand. Central's own console gives Ministry/ district staff:

  • A schools registry and per-school sync status.
  • Cross-school search over students, guardians and staff by name — matches a full "First Last" query, not just one half of it, and shows which school each result belongs to.
  • On-demand case-file detail for one student or guardian at a time — enrolment, attendance, guardians, consents, report-card status — reachable instantly when genuinely needed (for example, assisting a police inquiry about a specific family without the Ministry needing to contact the school directly), never held or broadcast in bulk.
  • Aggregate dashboards — attendance, enrolment, billing (summary totals only, never per-family), and a district-level illness/health rate (normalized per 100 enrolled students, so a raw count never unfairly favours a smaller district) — by school or rolled up by district, with CSV export.
  • Ministry account management — more than one real administrator account can now be created (role: Ministry Admin, Ministry Analyst or District Officer), not only the one break-glass account the very first release shipped with.

Three roles, deliberately asymmetric: Ministry Admin and District Officer can search and open case files (District Officer scoped to their own assigned schools); Ministry Analyst is refused individual search and case-file access outright, at the server, not just hidden in the interface — by design, an analyst role only ever sees aggregates.

5. The sync model — how a school reaches Central

A school links to Central from its own server (a companion window, Campus — Central Link Setup, not the browser console) with a URL and a bearer token Central issued when the school was registered. From then on:

  • What's sent is a curated, allowlist export built directly from the source models — never a wider "export everything" serializer trimmed down, to avoid a future field silently leaking through. Included: students, guardians, staff, attendance/incident/billing summaries (per-term totals, never a per-family invoice or application), consent status, report-card status. Excluded by default: health/medical data, custody notes, government IDs, narrative text (observation notes, incident descriptions), per-family billing or application detail, and (deliberately deferred, not yet built at all) who is authorized to pick a child up.
  • Full vs incremental. A sync is incremental by default (only rows changed since the last one), forced to a full reconcile when a school has never fully synced yet or it's been 7 or more days since the last full one — row-level tables only ever sweep (detect) deletions on a full sync, since an incremental bundle's absence of a row proves nothing; the four aggregate tables always send in full either way.
  • Transport. Server-to-server bearer-token auth (no session/CSRF — this is not a browser call); the bundle's own SHA-256 content hash is recomputed on arrival to catch tampering or corruption in transit; a schema-version check refuses a bundle Central doesn't yet know how to ingest.
  • On a timer, honestly: not yet. The sync agent and the "on-demand sync" button both work today (manage central_sync, or the companion window's Sync now button). What doesn't exist yet is an actual scheduled job that calls it automatically on a recurring basis — the worker process to run one now exists (§9's Campus Scheduler fix), but no Schedule row has been created for it. Stated here rather than implied, since "nightly sync" is the eventual intent but not the current reality.

6. Security & privacy

Campus's own security posture (built in from Phase 1, not a later pass): field-level AES-256-GCM encryption at rest for medical/allergy/medication data, custody and legal notes, government IDs, IEP content and uploaded documents; mandatory TOTP for every staff role; an append-only audit log of every write and every sensitive read; deny-by-default, object-level permissions (a parent sees only their own linked children; a teacher only their own groups); no card data ever reaches Campus (hosted-checkout payments only); no SMS path anywhere, email only.

Campus Central inherits the same account/audit/MFA foundation (the shared apps.accounts/ apps.audit code), plus its own additions specific to holding cross-school data:

  • Deny-by-default school scoping. A District Officer's queries are restricted to their assigned schools at the query layer itself (schools_visible_to()), not filtered after the fact.
  • Case-file access is on-demand only, never bulk-held — the explicit governing principle: Central should not constantly broadcast or hold full student detail by default, but when it genuinely needs detail (the police-inquiry scenario), that detail must be reachable instantly, not blocked behind contacting the school first.
  • A continuous disk-encryption check — BitLocker was previously verified only once, at install time; it's now re-checked on every manage check run, fails safe on any error, frozen builds only.
  • Its own encrypted, drilled backup/restore pipeline — mirrors Campus's own GPG-encrypted pg_dump approach exactly; Central had no backup tooling at all before this was built.
Open question, stated honestly rather than built wrong. Central's stored student/guardian PII (name, email, student number) is not field-encrypted the way Campus's own health/custody/government-ID data is. This was a deliberate decision, not an oversight: Central's cross-school search does direct SQL icontains matching on exactly those fields, and field-encrypting them would silently break that search outright — the same "find a student by name for a police inquiry" capability this paper describes as a core Central feature. A real fix needs searchable/blind-indexed encryption, which is its own, separately-scoped cryptographic engineering effort. Flagged here as an open item for a future release, not quietly shipped as "encrypted" when it isn't for these particular fields.

Parent/student portal — a restricted view: own-children only, real interactive schedule, attendance strip, released report cards, billing with online Pay, message threads, announcements/consents/incidents/IEP summary/bookings where they apply, guardian-initiated change requests that staff must approve.

9. Delivery: installers, backups & remote access

Both products install like a desktop application: one .exe, Windows services registered, boots on startup, no separate Python or Node install, no Docker. Campus-Setup.exe registers four services (PostgreSQL, App, Proxy, and — new — Campus Scheduler, the background-jobs worker that was configured but never actually registered before this pass: nothing on a timer could run for any feature until this was fixed, a product-wide gap, not specific to Central). Campus-Central-Setup.exe registers the Central equivalent, minus a scheduler service (Central has no scheduled jobs of its own yet).

Remote access (Campus) offers four modes: a Cloudflare named tunnel, WireGuard VPN, a plain gateway with your own domain, and — new — a Quick test tunnel (no Cloudflare account or domain needed, a random *.trycloudflare.com address) added after the named-tunnel flow was found to hang indefinitely for an account with no domain already added as a zone. The quick mode's own tradeoff is stated plainly to whoever enables it: the address changes every restart and no access policy can be attached to it — fine for a one-off test, not for ongoing access.

Backups (both products) use the same GPG-encrypted pg_dump pipeline, including the .env's encryption key inside the encrypted archive so a restore onto a fresh install (which would otherwise generate a different key) can actually read the encrypted fields back. Neither product schedules a backup automatically — that is an operator's own Task Scheduler entry, documented in the Technical & Troubleshooting Guide.

12. Known limits, stated plainly

  • Campus Central's sync is not yet on an automatic schedule — the worker now exists (§9), but no recurring job has actually been created for it; sync today is on-demand (manual button / command) only.
  • Campus Central does not field-encrypt the student/guardian PII its own cross-school search matches against (§6) — a deliberate, flagged trade-off against breaking that search, not yet resolved with searchable encryption.
  • Pickup-authorization data (who may collect a child) is not synced to Central at all — explicitly deferred by its own decision, not yet designed.
  • Campus Central has no in-console "Backups" page — only the scripts' own output, meant for a scheduled task.
  • The Kanoo (CaribPay) payment gateway for Bahamas-registered merchants is not built; Stripe is documented as unavailable to Bahamas-registered merchants, so a Bahamas install records online card payments only through Paystack/Flutterwave today, or by hand.
  • No multi-school import tool and no self-serve licensing (e.g. LemonSqueezy) exist yet — every install today is set up directly by Dunware Solutions.
  • Translation/i18n is investigated but deliberately parked — Django's i18n flag is on but unused, the Next.js frontend has no translation scaffolding and well over a thousand hardcoded English strings.
  • No macOS build exists for either product; both are Windows-only today.
  • Campus Central has no published price (§10).
