1. Architecture, in one page

LayerWhat it is
BackendDjango 5.2 + Django REST Framework, frozen with PyInstaller (onedir) into campus-app.exe — no separate Python install needed on the box. campus-app.exe serve runs the web tier; campus-app.exe manage <command> runs any Django management command.
FrontendNext.js 15, built as a fully static export (frontend/out) — no Node runtime on the box; served straight off disk by Caddy.
DatabasePostgreSQL 16, bundled and run as a Windows service.
ProxyCaddy — TLS termination, HTTP→HTTPS redirect, serves the static frontend, reverse-proxies /api /admin /static /media to the app.
Process managerNSSM wraps the app and the proxy as real Windows services (Postgres registers itself with pg_ctl register).

Services

Campus Appcampus-app.exe serve --host 127.0.0.1 --port 8001The frozen Django/DRF backend under waitress. Loopback only.

Campus RemotecloudflaredExists only if Cloudflare Tunnel remote access was turned on (see the Remote access section of docs/DEPLOYMENT.md).

The system is single-tenant and on-premises — one install per school, nothing shared, nothing sent to a third-party cloud unless the school deliberately sets up remote access or an online payment gateway.

2. Installing fresh

  1. Run Campus-Setup.exe as Administrator (it prompts). It lays out C:\ProgramData\Campus, stages the app, Postgres, Caddy, NSSM, GnuPG and the GTK3 runtime, and adds a Campus Start Menu group: Campus (opens the site), Campus — Remote Access Setup, and Campus — Payments Setup. A desktop shortcut is optional.
  2. install.ps1 runs automatically at the end, elevated. It generates unique secrets into .env and locks it down, initialises Postgres and registers the three services, runs migrations and collectstatic, templates the Caddyfile, trusts the local HTTPS certificate, and finally verifies that all services exist and https://<host>/ answers — if any of that fails it throws rather than report success.
  3. It checks (and warns, but does not block, if not) that the data drive is BitLocker-encrypted.
  4. Open https://localhost/ (or the configured hostname — §11). The very first visit shows "Welcome to Campus": create the first superadmin there, then enrol its authenticator app. That screen disables itself as soon as a superadmin exists. (The headless equivalent is campus-app.exe manage create_admin; create-campus-admin.ps1 exists for installs whose frozen exe predates it.)
  5. Keep a separate copy of FIELD_ENCRYPTION_KEY in secure custody. Read it from C:\ProgramData\Campus\app\.env (elevated). Current backups carry it inside the encrypted archive, but a spare copy covers archives made by older versions of the backup script and a lost passphrase-holder (§18).
  6. Sign in, then use School settings to name the school and add its logo, address and principal.
  7. Set the country, currency and whether the school collects fees, if it isn't a default — in the console under School settings → Region & fees, or from the command line: campus-app.exe manage set_site_config --country BS --currency BSD (and --collects-fees no for a fee-free school, which hides Billing entirely). One currency per install — see §7.
  8. Run campus-app.exe manage seed_demo --force only on a demo or training box — every record it creates is synthetic, and it refuses to run under a production profile without --force.

install.ps1 also accepts -LanHost, -Country and -Currency when run by hand.

3. Updating a live install

Two supported routes; both keep the database, media, .env and audit log.

  • Run the new Campus-Setup.exe over the existing install. It swaps the application files, re-runs migrations and restarts the services. (The bundled Caddyfile is only laid down when none exists, and a pristine Caddyfile.template always ships beside it, so a reinstall no longer resets a working proxy — see §14.13 for the older behaviour.) Uninstalling separately asks "Keep Campus data (database, media, audit log)?", default Yes.
  • The lighter route: repair-campus.ps1 -RefreshAppFrom … -RefreshFrontendFrom … -RefreshScriptsFrom … (§6) — swaps only what changed and re-migrates automatically.
Every installer that is handed off as ready for a fresh install must already contain every fix that has been built and tested — never only a hotfix (§10). Before telling anyone an installer is ready: rebuild the frozen backend and the frontend static export from current source, run the full test suite, run manage check against the fresh freeze, and only then compile. A fresh install that depends on a hotfix to be correct is a packaging failure, not an acceptable interim state.

4. Building from source

Prerequisites on the build machine: Node.js (for the frontend), the Python virtualenv at backend\.venv with requirements\build.txt installed, Inno Setup 6 or 7, and the third-party binaries staged in deploy\_thirdparty\ (§5).

cd frontend
npm run build                                    # -> frontend\out\  (static export)

cd ..\backend
.\.venv\Scripts\pip install -r requirements\build.txt
$env:DJANGO_SETTINGS_MODULE = "config.settings.prod"
$env:SECRET_KEY = ("x" * 60)                     # any 50+ char placeholder — freeze time only
$env:FIELD_ENCRYPTION_KEY = [Convert]::ToBase64String([byte[]]::new(32))   # any 32-byte base64 placeholder
.\.venv\Scripts\pyinstaller.exe ..\deploy\campus.spec --distpath ..\dist --workpath ..\build --noconfirm

..\dist\campus-app\campus-app.exe manage check   # smoke-test the freeze (same env vars as above)

cd ..\deploy
& "C:\Program Files\Inno Setup 7\ISCC.exe" campus.iss     # -> dist\installer\Campus-Setup.exe

Use the prod settings for the smoke test. The dev settings import django_extensions, which is deliberately not bundled, so manage check fails on the frozen exe under them — that failure is expected, not a bug.

Timing and size. The full compile with everything staged takes about 7 minutes and produces an installer of roughly 294 MB (about 37 MB with nothing staged). Run it in the background.

Inno Setup path. Check both C:\Program Files\Inno Setup 7\ISCC.exe and the Inno Setup 6 path if a script can't find it.

The two companion windows are not separate installers. campus.iss copies remote-setup-ui.ps1 and campus-payments-setup-ui.ps1 into {app}\scripts and creates their Start Menu shortcuts, so one iscc run keeps them current.

Release checklist

  1. Backend: ruff, manage check --deploy --fail-level WARNING, makemigrations --check --dry-run, and the full pytest suite all clean.
  2. Frontend: tsc --noEmit, next lint, next build clean.
  3. Freeze, smoke-test the freeze, compile, and confirm the installer's timestamp and size are new.
  4. Regenerate any of the three PDFs whose subject changed: backend\.venv\Scripts\python.exe docs\pdf-src\render_docs.py (sources in docs\pdf-src\).

5. Staging third-party dependencies

deploy\install-dependencies.ps1 is a technical-staff tool, separate from and never run by the application's own installer (campus.iss/install.ps1 never invoke it, and it is not bundled into Campus-Setup.exe). It prepares the build machine by fetching and staging the third-party binaries campus.iss can bundle into deploy\_thirdparty\, in exactly the layout the installer expects. It detects what is already staged and skips it, and needs no elevation — it only ever writes under deploy\_thirdparty\.

powershell -ExecutionPolicy Bypass -File deploy\install-dependencies.ps1              # fetch everything missing
powershell -ExecutionPolicy Bypass -File deploy\install-dependencies.ps1 -CheckOnly   # report only
powershell -ExecutionPolicy Bypass -File deploy\install-dependencies.ps1 -Only gtk3,gpg
powershell -ExecutionPolicy Bypass -File deploy\install-dependencies.ps1 -Force       # re-fetch even if already staged

The names it understands are caddy, nssm, gtk3, gpg and postgres. Each is individually optional — a partial _thirdparty\ tree still compiles a working, reduced installer, and install.ps1 degrades with clear messages for whatever is absent.

ComponentPinned versionStaged atLicence
PostgreSQL, portable16.15_thirdparty\pgsql\PostgreSQL
Caddyv2.11.4_thirdparty\caddy\caddy.exeApache 2.0
NSSM2.24_thirdparty\caddy\nssm.exe (beside Caddy)Public domain
GnuPG (backup encryption)2.5.22 standalone_thirdparty\gpg\GPLv3

If you skip _thirdparty\remote\, the installer still builds and works; only a site that will use Cloudflare Tunnel or WireGuard needs those binaries. gtk3 and gpg ship as NSIS installers whose manifests demand elevation, so the script extracts them by direct invocation with /S /D=<path> — not Start-Process (§14.11).

Running it if you've never used PowerShell before

This is the same tool, in the order you'd actually do it, assuming nothing. It does not need Administrator — if something asks you to "Run as administrator" while you follow these steps, that is not this tool.

  1. Have the whole Campus source folder on this machine (for example D:\Solutions\dunware-campus) — the whole folder, not just the script.
  2. Open PowerShell. Press the Windows key, type PowerShell, press Enter on "Windows PowerShell". A blue or black text window opens — this is normal.
  3. Move into the deploy folder. Type cd, a space, then the full path to the deploy folder (for example cd D:\Solutions\dunware-campus\deploy) and press Enter. Nothing dramatic happens — you're just "standing inside" that folder.
  4. Run the check. Type exactly powershell -ExecutionPolicy Bypass -File install-dependencies.ps1 -CheckOnly and press Enter. It only looks — it downloads and changes nothing, so run it as often as you like. You'll see a list such as: 
    caddy      present
nssm       present
gtk3       MISSING
gpg        present
postgres   present
    present means nothing to do; MISSING means it needs fetching.
  5. If everything says "present", you're done.
  6. If something says "MISSING", run the same command without -CheckOnly. It downloads only the missing pieces (PostgreSQL is the big one, about 330 MB — be patient) and prints each as it completes.
  7. Read the summary table at the end. Each row should say Installed or Skipped (already staged). A row beginning FAILED means that one piece didn't complete.
If a row says FAILED: the most common cause by far is no internet connection, or a network that blocks GitHub and download sites (common on locked-down school or office networks). Try another network, or send the exact red FAILED line to whoever supports your Campus — that single line is normally enough to tell what went wrong.

6. Repairing & uninstalling

repair-campus.ps1, run elevated, fixes the known install failure classes without a full reinstall:

powershell -ExecutionPolicy Bypass -File C:\ProgramData\Campus\scripts\repair-campus.ps1

With no flags it re-registers any missing service, re-templates the Caddyfile if it was reset to the raw template, strips a UTF-8 BOM from .env, and re-trusts the local HTTPS certificate. It is idempotent — safe to run repeatedly. To push new code into a live install:

repair-campus.ps1 `
  -RefreshAppFrom      <repo>\dist\campus-app `   # swaps campus-app.exe + libs, keeps .env/media/staticfiles, re-migrates
  -RefreshFrontendFrom <repo>\frontend\out `      # swaps the served SPA
  -RefreshScriptsFrom  <repo>\deploy             # swaps the day-2 *.ps1 scripts themselves

Each flag is independent — pass only what changed. -RefreshAppFrom stops Campus App for the copy and restarts it after re-migrating; -RefreshFrontendFrom stops Campus Proxy so Caddy's file handles don't block the copy.

-RefreshAppFrom does not refresh C:\ProgramData\Campus\scripts\. Those scripts come from the full installer or from -RefreshScriptsFrom. A site whose backup.ps1 is older than its app can misbehave in specific ways (§14.12).

Uninstall is the standard Windows uninstall (Settings → Apps). It asks whether to keep the data (database, uploaded documents, audit log) for a future reinstall or delete it permanently; uninstall-services.ps1 stops and removes the services.

7. Online payments — connecting a gateway

Campus works with manual payments out of the box. To let families pay online, connect the school's own merchant account with the Campus — Payments Setup window (Start Menu; it self-elevates). Campus never sees a card number: checkout is the provider's hosted page (PCI SAQ-A), the provider emails the receipt, and the money goes straight to the school's account.

Connecting a gateway

  1. Open Start Menu → Campus → Campus — Payments Setup.
  2. Pick Paystack, Flutterwave or Stripe (or Manual for none). Kanoo (Bahamas) is not offered until its provider grants API access; a Bahamas install records payments manually meanwhile.
  3. Choose Test or Live mode and enter the keys from the provider's dashboard.
  4. Click Test connection. It tests exactly the values in the form, without saving them.
  5. Click Apply. The secret key is stored AES-256-GCM encrypted in the database — never in .env, logs or the support bundle.

The window is a front end for two commands you can also run from an elevated shell in C:\ProgramData\Campus\app\:

campus-app.exe manage set_gateway_config --gateway paystack --mode test --public-key <pk> --secret-key <sk>
campus-app.exe manage payments_test [--gateway ... --mode ... --public-key ... --secret-key ...]   # tests saved or supplied values

What each provider needs

ProviderKeysWatch out for
PaystackPublic + secret keyA merchant account is single-currency — one of NGN, GHS, ZAR, KES or USD, matching the country it was registered in. Charging any other currency is rejected by Paystack as "Currency not supported by merchant"; that is Paystack's rule, not a Campus fault.
FlutterwaveThe classic v3 pair: FLWPUBK-… and FLWSECK-…Newer dashboards show v4 "Client ID / Client Secret / Encryption Key" by default. Those are not what Campus uses; ask Flutterwave support for, or find, the classic v3 keys. Campus uses Flutterwave's hosted checkout, so it never handles card details.
StripePublishable + secret keyStripe is not available to merchants registered in every country (for example, not the Bahamas). Check the school's country is supported before promising it.

Country, currency and fees

A Campus install bills in one currency, and the gateway account must be able to charge in it. Set it in the console under School settings → Region & fees (country, currency, locale, and a "collects tuition / fees" switch), or with campus-app.exe manage set_site_config --country ZA --currency ZAR. Once any invoice exists the currency is locked and the console's currency box is disabled; changing it then is a deliberate command-line step: set_site_config --currency … --force. (The console's hint mentions a change_currency command — that command does not exist; use set_site_config.) Turning the fees switch off, or --collects-fees no, hides Billing everywhere for a school that charges nothing through Campus. Every invoice carries its own currency and every screen displays it.

How a payment is confirmed

  • A parent presses Pay in the portal (or staff generate a Payment link on an invoice). Campus creates a payment attempt and sends the family to the provider's checkout.
  • A family with several children may pay several invoices in one charge — they must share a billing guardian and a currency — and may pay part of the balance. The amount is split back across the invoices proportionally.
  • When the family returns to Campus, the return page asks the provider whether the payment succeeded (checking every few seconds for about two minutes, then offering Check again). Only a success whose amount and currency match is recorded as a payment. A mismatch is never applied automatically; the family is told to contact the office and not pay again.
  • There is no background reconciliation job yet. A payment is confirmed when the family's return page (or a status check) asks. If a family pays but never returns to Campus, the money is in the school's provider account but the invoice stays unpaid in Campus — verify it in the provider's dashboard and record it with Mark paid, quoting the provider's reference.
  • Refunds are manual: record a Credit in Campus and return the money through the provider's own account.

Test data

manage seed_demo --currency ZAR builds demo data in a chosen currency (default ZAR). manage seed_paystack_currencies adds one small payable test invoice for each currency Paystack supports (needs a debug profile or --force; --flush replaces them). Demo guardians use @example.com addresses because Paystack's own validator rejects the .test top-level domain.

8. Backups & restore — how the tooling works

backup.ps1 takes a custom-format pg_dump, the whole media\ directory (encrypted documents, photos, signatures) and a copy of app\.env (stored as env.backup), packs them into one archive, and encrypts it with GnuPG (--symmetric, AES-256) using an operator-supplied passphrase. The plaintext archive is deleted the moment encryption succeeds — and also if encryption fails, along with any half-written file. The .env copy is there because it holds the FIELD_ENCRYPTION_KEY that every encrypted field and document depends on (§18); archives made by an older version of the script do not contain it. Archives older than -RetentionDays (default 30) are pruned on each run. restore.ps1 reverses it: decrypt, stop Campus App, copy only the FIELD_ENCRYPTION_KEY line from env.backup into the target .env (never the whole file — a fresh install's own DATABASE_URL and Postgres password must not be overwritten), pg_restore --clean --if-exists, restore media\, run migrations (so a backup from before a schema change still restores), restart. For an archive with no env.backup it prints a warning. Both scripts have a -Simulate switch for drilling the archive/encrypt/decrypt path.

  • GnuPG is bundled at C:\ProgramData\Campus\gpg; the scripts use it first (with GNUPGHOME at gpg\home, touching no user profile) and fall back to a gpg on PATH. With neither, backups fail with a clear "gpg was not found".
  • The passphrase is chosen by the operator. Nothing generates or stores it — not the installer, not Campus. It is the encryption key: if it is lost, every archive is unrecoverable. Type it when asked, or set CAMPUS_BACKUP_PASSPHRASE in the scheduled task's environment for unattended runs.
  • From the console: administrators see Backups — a health summary plus every run. Run backup now starts the same script detached, tied to a tracked run record, so success or failure is visible without shell access. The passphrase is entered per run and passed only in that process's environment. Guards: at most one manual run in flight, and a 10-minute cooldown between runs. Output goes to logs\backup-manual.log.
  • A run that never reports back is marked FAILED automatically after 30 minutes, and the summary turns amber if the newest success is over 48 hours old or the latest run failed.
  • Existing installs only get the key-carrying backup once their scripts are refreshed — install the new Campus-Setup.exe or run repair-campus.ps1 -RefreshScriptsFrom <repo>\deploy (§6) — and should then take a fresh backup, since every earlier archive lacks the key.
  • Restore is drilled, not assumed: restore.ps1 also records a verification run. See docs/BACKUP_RESTORE_DRILL.md for the executed drill.

9. Field-support tools

Run these in an elevated shell on the box (campus-app.exe lives in C:\ProgramData\Campus\app\):

campus-app.exe manage support_bundle
campus-app.exe manage support_tail app|proxy|db|remote [-n N]
campus-app.exe manage support_sql "<query>" --operator "<your name>" [--write]

support_bundle produces one redacted ZIP — logs, health, service states, a secrets-stripped .env, table row counts, build stamp — and contains no student data, so it is safe to email or carry away. support_sql is read-only (and rolls back automatically) unless --write is passed; every run writes one append-only audit entry.

10. The hotfix overlay — and its one hard rule

To patch a logic-only bug on a live box without a full rebuild, drop the corrected .py file under C:\ProgramData\Campus\app\hotfix\ at its real package path (for example hotfix\apps\grades\services.py), then restart Campus App. It shadows the frozen copy. Active hotfixes are logged at startup, flagged by manage check (core.W001), and shown in the support bundle and the console's Remote access page — a patched box is never invisible.

It cannot add a dependency or change a model or migration; those need a real patched build applied with repair-campus.ps1 -RefreshAppFrom.

A fresh install or reinstall does not carry the hotfix folder over. It is empty on the new box, so a fix that only ever lived there quietly regresses the moment someone reinstalls — this has happened, and cost a debugging session tracing a "reintroduced" bug back to a wiped hotfix folder. Treat the overlay as a same-day stopgap only. Fold every hotfix into a real release and clear the folder once that release ships.

11. Changing the address from localhost

By default Campus answers at https://localhost/. To make it answer to a name on the LAN (for example https://campus/):

  1. Re-run install.ps1 or repair-campus.ps1 with -LanHost campus (or your chosen name). This re-templates the Caddyfile, updates ALLOWED_HOSTS / CSRF_TRUSTED_ORIGINS / PUBLIC_BASE_URL in .env, and re-issues the local TLS certificate for that name.
  2. The name must still resolve for other machines — add a DNS entry on the router or local DNS server, or a line in each client's hosts file (C:\Windows\System32\drivers\etc\hosts) pointing the name at the server's LAN IP.
  3. Open the new address once in a browser on the server itself to trust the fresh certificate (or run repair-campus.ps1 again), and import C:\ProgramData\Campus\campus-local-ca.crt on other PCs (§14, certificate warning).

Access from outside the LAN is a separate, opt-in feature — Campus — Remote Access Setup (Tunnel / WireGuard / Gateway modes) and docs/REMOTE_ACCESS_AND_YOUR_DATA.md — not this hostname setting.

12. Data model, security & privacy — the short version

Full detail: docs/DATA_MODEL.md (every PII field, its purpose and retention) and docs/PII_SECURITY.md (the control matrix). In brief:

  • Encryption at rest — medical/allergy/medication data, custody and legal notes, government IDs, IEP content, gateway secret keys and uploaded documents are AES-256-GCM encrypted, not just access-controlled. The key (FIELD_ENCRYPTION_KEY) lives only in the ACL-locked .env; production refuses to start without it. Lose that key and the encrypted fields are unrecoverable — backups carry a copy inside the encrypted archive, and you should keep another in secure custody.
  • Role-based access — deny-by-default permissions; a parent sees only their own linked children (Student.is_visible_to() / visible_queryset() is the single scoping authority for staff API and portal alike); a teacher sees only the groups they staff.
  • MFA — mandatory TOTP for every staff role. Account lockout after repeated failures, and Argon2 password hashing.
  • Audit log — append-only; every create/update/delete and every read of a sensitive record, with actor, IP and timestamp but no field values. No edit or delete path exists in the app.
  • Retention & erasure — a configurable window per record type, a legal-hold flag that blocks both automated retention and manual erasure, and audited export_student / erase_student commands.
  • No card data ever reaches Campus. Online payments use each provider's hosted checkout (PCI SAQ-A); Campus stores only a reference, amount, status and an encrypted copy of the last verification response. Payments recorded by hand hold a method and reference, never a card number.
  • No SMS path anywhere — communication is email-only, by design.

13. How the calendars and grading schemes work

Every session lives in one table (scheduling.SessionOccurrence), but three UI surfaces read it for three audiences — this trips people up often enough to spell out:

ViewShowsWhy
Scheduling → Calendar (console)Closures & early dismissals only — no individual class periodsWhole-school view; at hundreds of students, every class period on one calendar is unreadable
Students → Timetable (console)One student's real class-by-class day — homeroom and every course-of-study section, never overlappingScoped with ?student=, resolved server-side to every group they're actively enrolled in
Portal → Upcoming scheduleThe same as that student's Timetable, for the guardian's or student's own child(ren) onlyBacked by /api/portal/calendar/ — same payload shape, authorised via is_visible_to()

The frontend component is the same one, ScheduleCalendar.tsx: a showSessions prop (default true) is what the Scheduling page sets false to become the exceptions-only view, and a fixedStudentId prop locks a Timetable/portal instance to one student.

Which weekday a given course-of-study subject falls on is hardcoded only in the synthetic demo data (seed_demo.py). A real deployment's timetable comes from that school's session templates — there is no built-in assumption about which days a subject runs.

Report-card grading. grades.GradingScheme (+ GradeBand) is a school's grading policy — the letter/level bands a percentage falls into, and whether a GPA is used at all. GradingScheme.activate() deactivates every other scheme in one transaction, so exactly zero or one is ever active. Four presets ship via a data migration (not a fixture, so they are always present): Bahamas 4.0 GPA, Ontario elementary 4-level, South Africa NCS 7-point, Botswana letter bands. generate_report_card() freezes the active scheme and the computed cumulative_gpa (an unweighted mean across GPA-bearing entries — there is no credit-hour model) onto the ReportCard at generation time, so changing the scheme later never rewrites a card that already went home.

14. Known issues — root cause and fix

Every entry below was found by actually running the software, not caught in review.

14.1 · Install partially completes — only "Campus PostgreSQL" registers, browser refuses to connect

Symptom

After a fresh install, Get-Service "Campus*" shows only Campus PostgreSQL and https://localhost/ refuses to connect. Running campus-app.exe manage migrate by hand throws an AttributeError such as module 'apps.core.models' has no attribute '_school_logo_path'.

Root cause

The frozen campus-app.exe inside that Campus-Setup.exe was built from a stale or inconsistent source snapshot — a migration expects a symbol its own bundled models.py doesn't have. install.ps1 runs migrations early with $ErrorActionPreference = "Stop" and deliberately throws rather than continue, so the run aborts before it registers Campus App and Campus Proxy; Postgres, registered earlier, is all that's left.

Fix

Rebuild the installer clean from current, verified source (§4) and run manage check against the fresh freeze before compiling, so this class of bug never reaches an install. Do not patch around a bad binary. To unblock a broken install when a known-good build exists, repair-campus.ps1 -RefreshAppFrom re-migrates against the corrected exe.

14.2 · Services never registered, install reports success anyway (historical, fixed)

Symptom

https://localhost/ refuses to connect after an apparently successful install.

Root cause

campus.iss originally ran install.ps1 with runascurrentuser, which does not inherit Setup's elevated token; nssm's CreateService calls silently failed and the script still exited 0.

Fix

runascurrentuser removed. install.ps1 now hard-guards on elevation, and Register-CampusService confirms each service with Get-Service instead of trusting NSSM's exit code. The final verification step throws if any service is missing or the site doesn't answer.

14.3 · 404 at "/" behind a healthy proxy chain (historical, fixed)

Symptom

curl http://localhost/ returns 404 with server: waitress and via: 1.1 Caddy — the chain is up but nothing serves the page.

Root cause

The Caddyfile proxied every non-API path to Django, which has no route for / and no static root.

Fix

Caddy now serves the exported frontend itself (root + try_files + file_server) and proxies only /api /admin /static /media. {$CAMPUS_WEB_ROOT} templates to <InstallRoot>\app\frontend_out.

14.4 · A staff-chat popover opened almost entirely off-screen

Root cause

The panel was position:absolute; right:0 inside a wrapper only as wide as the bell (~36 px) near the left edge of the sidebar, so a 380 px panel's right edge landed near x=210 and its left edge near x=-170.

Fix

Anchored from the left edge so it opens rightward into the content area.

14.5 · The same popover then painted behind the page content

Root cause — a general CSS lesson

The shared "glass" card style sets backdrop-filter, which creates its own stacking context even on an unpositioned element. The sticky sidebar is also its own context and precedes the content in the DOM; two contexts with no explicit z-index paint in DOM order, so every glass card outranked the whole sidebar, including anything nested in it. No z-index inside the sidebar could win.

Fix

Render the popover through a React portal onto document.body as position:fixed with coordinates from the trigger's getBoundingClientRect() — the technique the command palette already used — sidestepping DOM position entirely.

14.6 · A failed action (for example "Send") did nothing visible

Root cause

The mutation had no onError handler.

Fix

Wired to the app's standard toast-and-message pattern, like every other form.

14.7 · An error popup read literally "…is not valid JSON" (app-wide)

Root cause

The shared API client called JSON.parse() on every response. Any non-JSON reply — Django's HTML 404 for a route a stale backend doesn't have yet, a proxy error page, a truncated response — threw the browser's native parser error before it could be wrapped.

Fix

The parse is caught and turned into a readable error ("The server returned an error page (HTTP <code>) instead of a normal response — it may be out of date, restarting, or misconfigured"). This reaches every screen.

14.8 · One staff role saw nobody in a "message" recipient picker

Root cause

The staff-directory endpoint the picker depends on was gated to admin roles; a front-desk request got a 403 and the picker was silently empty (broadcast options don't use that endpoint, so they kept working).

Fix

Opened to every staff role, with its query scoped to staff accounts only so it doesn't newly expose parent or student accounts.

14.9 · A calendar group filter silently did nothing

Root cause

Every record uses a UUID primary key, but the calendar code typed group ids as numbers (Number(uuid) is NaN, falsy), so the filter parameter was never sent. The backend was already correct.

Fix

Ids retyped as strings throughout the calendar stack; a repo-wide search found no other instance.

14.10 · Pages rendered tiny, in a corner of the window

Root cause

The root layout had no viewport meta tag; some browser and display combinations then lay the page out at a fixed desktop width and scale it down.

Fix

Added the standard {width:"device-width", initialScale:1} viewport export once at the root, fixing every route and modal.

14.11 · Report-card and document PDFs silently generate as .html — no error anywhere

Symptom

A generated report card (anything through apps/grades/services.py html_to_pdf()) is stored and downloadable as .html, not .pdf. Nothing in the UI or logs calls it a failure — it is the designed fallback (PdfEngineUnavailable), not a crash.

Root cause

WeasyPrint is a thin Python wrapper around real native libraries — Cairo, Pango, GObject, HarfBuzz, Fontconfig. PyInstaller's own hook does not bundle them (the freeze log always warns "WeasyPrint could not import some external libraries"). Without them import weasyprint raises, html_to_pdf() catches it, and the code falls back to .html by design — so the gap ships unnoticed unless someone opens a generated document and checks its extension.

Fix

The GTK3 runtime for Windows is staged as its own third-party component at deploy\_thirdparty\gtk3\ and bundled by campus.iss into C:\ProgramData\Campus\gtk3. campus_app.py's _ensure_native_pdf_libs() calls os.add_dll_directory() on gtk3\bin once, at the top of main(), before either serve or manage runs.

A trap worth recording: PATH is not enough

Adding gtk3\bin to PATH lets cffi load the first DLL, but it fails with OSError … error 0x7e (ERROR_MOD_NOT_FOUND) as soon as that DLL loads its own dependencies, even though they sit in the same folder — Windows' Safe DLL Search Mode doesn't extend a PATH directory to a loaded DLL's transitive dependencies. os.add_dll_directory() (Python 3.8+, Windows) does. Confirmed by testing both ways against the real frozen exe.

Re-staging the runtime

The upstream GTK3 runtime is an NSIS installer whose manifest demands elevation, which blocks Start-Process. Extract it by direct invocation: & ".\gtk3-runtime-installer.exe" /S "/D=C:\extract\target" (/D= last, absolute, unquoted internally — note this is not Inno Setup's /DIR=, and innoextract rightly refuses it). Copy the whole tree (bin lib share etc, about 137 MB) into deploy\_thirdparty\gtk3\; install-dependencies.ps1 -Only gtk3 does all of this.

Verify it really works

cd C:\ProgramData\Campus\app
.\campus-app.exe manage shell -c "from apps.grades.services import html_to_pdf; pdf = html_to_pdf('<h1>test</h1>'); print(len(pdf), pdf[:8])"

A real result looks like 7330 b'%PDF-1.7'. If it raises PdfEngineUnavailable, confirm C:\ProgramData\Campus\gtk3\bin\libgobject-2.0-0.dll exists — if not, the installer was built without the GTK3 payload (an optional component; the app still runs, with document PDFs falling back to .html).

14.12 · A manual backup shows "Running" for hours and never finishes

Symptom

After Backups → Run backup now, the run stays Running indefinitely.

Root cause

The console launches backup.ps1 -RunId … -Kind MANUAL, but the copy in C:\ProgramData\Campus\scripts\ pre-dates those parameters. -RefreshAppFrom never refreshes scripts\, so PowerShell rejects the unknown parameters before the script body runs and nothing ever records a result.

Fix

Refresh the scripts: repair-campus.ps1 -RefreshScriptsFrom <repo>\deploy (or run the full installer). The app now also fails fast — a launch that exits non-zero within about 12 seconds is marked FAILED at once with the exit code, a stale-script hint and the log tail (the console shows it inline), and any run still Running after 30 minutes is flipped to FAILED on the next page load.

14.13 · Reinstalling over a working install gave "refused to connect" (historical, fixed)

Symptom

After running a newer Campus-Setup.exe over a working install, the site refused connections; Campus App and Campus Proxy were gone and the Caddyfile had reset to the raw template.

Root cause

campus.iss re-laid the Caddyfile every time (ignoreversion = always overwrite), and the reinstall's install.ps1 step didn't re-register the services.

Fix

The bundled Caddyfile is now onlyifdoesntexist, a pristine Caddyfile.template always ships beside it, and install.ps1 seeds Caddyfile from the template if missing. To recover a box hit by the old behaviour, run repair-campus.ps1 elevated with no flags. Don't reinstall just to get a Start Menu shortcut — launch the window's script directly.

14.14 · Paystack rejects a charge — "Currency not supported by merchant"

Root cause

A Paystack merchant account charges in exactly one currency, matching the country it was registered under. The install's invoices were in a different one.

Fix

Bill in the account's currency (§7). A stray .test email domain on a demo guardian also fails Paystack's validator; demo data now uses example.com. Once invoices exist, the site currency is locked in the console — change it deliberately with set_site_config --currency … --force.

15. General diagnostics playbook

A service won't start, or keeps stopping

  1. Read C:\ProgramData\Campus\logs\Campus-App.log (or Campus-Proxy.log) — NSSM writes stdout and stderr there. campus-app.exe manage support_tail proxy tails a log.
  2. Check the other two services first: Campus App needs Campus PostgreSQL reachable; Campus Proxy needs Campus App answering on 127.0.0.1:8001.
  3. Run the exe in the foreground from an elevated shell in C:\ProgramData\Campus\app\ to see the real startup error: .\campus-app.exe serve --host 127.0.0.1 --port 8001.

"Refused to connect", a blank page, or "This site can't be reached"

  1. Get-Service "Campus*" — are all three Running? If only Postgres is, see §14.1–14.2: almost always a partial install, not a runtime fault.
  2. Test-NetConnection 127.0.0.1 -Port 5432 (Postgres), -Port 8001 (app), -Port 443 (proxy) isolates the layer that's down.
  3. Run repair-campus.ps1 elevated with no flags — it re-registers anything missing and re-templates a reset Caddyfile. A repeated redirect loop usually means the proxy isn't being told the request already arrived over HTTPS; check X-Forwarded-Proto trust in the Caddyfile.

A report card or document is .html instead of .pdf

  1. Not a fault by itself — the designed fallback when the PDF engine isn't available (§14.11). Check whether it should be: Test-Path "C:\ProgramData\Campus\gtk3\bin\libgobject-2.0-0.dll".
  2. If missing, the installer was built without the GTK3 payload. Reinstall from one that has it, or stage _thirdparty\gtk3 and copy it to C:\ProgramData\Campus\gtk3 — no reinstall needed, since the app only checks for the folder at startup.
  3. If present and it still falls back, run the smoke test in §14.11 rather than guessing.

Database errors ("connection timeout expired" / "connection refused")

Almost always Campus PostgreSQL is stopped — not a credentials problem (a bad password fails fast with "password authentication failed", not a timeout). Start-Service "Campus PostgreSQL", wait a few seconds, retry.

Browser shows a certificate warning

Expected on any machine other than the server, on first visit. Copy C:\ProgramData\Campus\campus-local-ca.crt from the server into that machine's Trusted Root Certification Authorities store (or push it by Group Policy), then fully restart the browser. If the server itself warns, re-run repair-campus.ps1 — it re-trusts the local CA.

A migration fails on an otherwise healthy install

Check whether a hotfix overlay is active (app\hotfix\ not empty) — an overlay out of sync with the schema causes confusing errors — and confirm the frozen build isn't stale (§14.1; manage check is the fast, database-free test). For a schema change that fails against existing rows: a plain AddField(unique=True) on a populated table fails with an IntegrityError on the shared default. The fix is always the same shape — add the column nullable, backfill real values in a data migration, then tighten it to non-null/unique in a third step; never a one-step unique add against live data.

A fix "disappeared" after a reinstall

Almost always a hotfix that was never folded into a release (§10). Check app\hotfix\; if it's empty and the behaviour regressed, the installer needs the fix built in.

A student's timetable looks wrong (overlapping classes, or every group in the school)

First confirm which build is running — support_bundle reports the build stamp. This symptom has previously been a box still running pre-fix code after a hotfix folder was wiped, not a live bug. If it persists on a current verified build, it's a real regression: report it, don't hotfix around it.

Demo or training data needs a clean reset

campus-app.exe manage seed_demo --force --flush

Regenerates the whole synthetic dataset. Never point this at a database holding real student data.

An online payment is missing from Campus

See §7 — with no background reconciliation job yet, a payment is only confirmed when the family returns to Campus. Check the provider's dashboard and record it with Mark paid.

Part II · Running Campus independently (outright purchase / self-managed)

Everything above applies whether or not Dunware Solutions is actively supporting an install. Everything from here is for an organization that has bought Campus outright and whose own technical staff will apply updates, run backups and maintain it. It is the same product and toolkit already described in Part I, organised around the questions an independent team asks first.

16. System requirements & sizing

Operating system64-bit Windows, desktop or Server (Windows 10/11, Server 2019/2022) — the installer targets x64compatible. Nothing prefers Server over Desktop; use your own IT standard.
CPU / RAMModest by design — Django behind waitress, PostgreSQL and Caddy serving one school on its LAN. 4 cores / 8 GB RAM is comfortable headroom for a single school; treat it as a sensible floor to plan from, not a load-tested figure for a given enrolment.

Off-premises access is opt-in (docs/REMOTE_ACCESS_AND_YOUR_DATA.md). Online payments need outbound HTTPS to the chosen provider only — no inbound port and no public address.
Client browsersAny current evergreen browser (Edge, Chrome, Firefox). Nothing is installed on a staff or parent machine beyond trusting the server's local certificate once (§15).

17. Version tracking & the update lifecycle

apps/core/version.py is the single source of build identity — CAMPUS_VERSION (currently 0.9.0) plus, on a frozen install, the exe's build timestamp. It shows in manage support_bundle and on the superadmin's Remote access page. Confirming it changed is the cheapest proof an update took.

How an update reaches an independently operated site

  • A new installer only (the common case): Dunware ships a rebuilt Campus-Setup.exe. Running it over an existing install is safe (§3). For a routine update the lighter path is repair-campus.ps1 -RefreshAppFrom … -RefreshFrontendFrom … -RefreshScriptsFrom …, which swaps the application in place, re-migrates automatically and touches only what it must.
  • Full source access (an outright code purchase): the organization's developers pull the updated source, follow §5 and §4 exactly as written, and apply the result the same way. Part I is sufficient on its own for this — there is no hidden Dunware-only build step.

Recommended procedure, every time

  1. Back up first (§8, §18) — before, not after, something goes wrong.
  2. Apply the update (either path).
  3. Run campus-app.exe manage check --deploy --fail-level WARNING to confirm the security posture survived, not merely that the app starts.
  4. Confirm the version/build stamp changed, then smoke-test: sign in, open a student, generate a report card (which also proves the PDF engine survived), and — if online payments are on — open the Payments Setup window and click Test connection.
  5. Migrations run automatically with -RefreshAppFrom and install.ps1; there is no manual schema step and no supported way to skip migrating.

18. Backup schedule, retention & disaster recovery

Backups are on-demand, not automatic, out of the box. Nothing in Campus runs backup.ps1 on a timer. Set one up on day one: a Windows Task Scheduler job that runs elevated as SYSTEM (or a dedicated service account) and calls powershell.exe -ExecutionPolicy Bypass -File C:\ProgramData\Campus\scripts\backup.ps1 with CAMPUS_BACKUP_PASSPHRASE set in that task's environment, at whatever cadence your recovery-point objective needs — nightly is a reasonable default for a system holding same-day attendance, incident and billing records — and copy the output off the machine. This is the single most important operational gap for a self-managed site to close.

Disaster recovery — new or repaired hardware

  1. Install Campus fresh on the replacement machine (§2). This makes a new, empty database, a new random DATABASE_URL password and a new FIELD_ENCRYPTION_KEY — all expected.
  2. Copy the most recent encrypted archive onto the machine.
  3. Run restore.ps1 against it with the correct passphrase. It puts the archive's original FIELD_ENCRYPTION_KEY into the new install's .env (it prints "Restored FIELD_ENCRYPTION_KEY from the backup") before restarting Campus App, leaves the new DATABASE_URL alone, and moves the data (students, guardians, grades, the audit log) into the fresh database and media store. If it instead warns that the archive has no env.backup, the archive came from an older backup script: put the original key from your custody copy into C:\ProgramData\Campus\app\.env (elevated), restart Campus App, then run the restore.
  4. Verify: sign in, spot-check records — open a student's health or IEP tab, which proves the encrypted fields decrypt — and confirm audit history survived (it is in the same database).

The same procedure is the correct way to migrate to different hardware on a planned basis.

The encryption key is what makes a restore usable. Medical and custody data, IEPs, government IDs, gateway keys and every uploaded document are encrypted with the FIELD_ENCRYPTION_KEY in .env, and a fresh install generates a different key. Current backups carry .env inside the encrypted archive and restore.ps1 puts the key back, so a normal restore needs nothing extra. Archives made by older versions of the backup script do not contain it — for those, and as insurance, keep a copy of that one value in secure custody (taken the day you install, and again if it is ever rotated). The backup passphrase (§8) likewise has to be stored somewhere other than the machine it protects. Lose both the archive's copy and your own, and the encrypted fields are unrecoverable.

Test your restores

A backup that has never been restored is a hope, not a plan. Restore to a spare or virtual machine on a real schedule (quarterly is a reasonable floor for legally sensitive child records) and confirm it works end to end, not merely that the script exits 0. docs/BACKUP_RESTORE_DRILL.md and docs/RETENTION_ERASURE_DRILL.md record Dunware's own drills against this exact tooling and are a template for yours.

19. Security & compliance — what becomes your responsibility

The security architecture (encryption at rest, MFA, the append-only audit log, object-level access control) is built into the application and does not change with who operates it — see docs/PII_SECURITY.md. What changes once a site is self-managed is who keeps the operational half of that posture current:

  • OS patching — Windows Update on the host is entirely yours.
  • Third-party versions — install-dependencies.ps1 pins tested versions (Caddy v2.11.4, NSSM 2.24, PostgreSQL 16.15, GnuPG 2.5.22, GTK3 3.24.31) rather than tracking "latest". Moving to a newer one is a deliberate act: update the URL, re-stage, rebuild and re-run the full gate (§4) before it goes near a live site.
  • Payment credentials — the school owns its Stripe/Paystack/Flutterwave merchant account, its KYC/compliance and its transaction fees. Keep live secret keys out of email and chat, rotate them in the Payments Setup window if exposed, and keep Test mode for training boxes only.
  • Audit log and retention — RETENTION_AUDIT_LOG_DAYS and related .env settings control how long time-boxed records are kept before run_retention anonymises them. Set them against your regulatory obligations; Dunware's defaults are a starting point, not a compliance determination.
  • Regular verification — manage check --deploy --fail-level WARNING costs nothing to run after any change or on a schedule, and catches configuration drift before it becomes an incident.
  • Reading the audit log — it exists to be read. The console viewer (administrators) is the day-to-day tool; support_sql (§9) covers what its filters can't.

Data-subject-rights tooling is built and now yours to operate under your own jurisdiction: manage export_student <id> (full decrypted export, audited), manage erase_student <id> (anonymise in place, blocked by a legal hold, audited), manage run_retention (the scheduled sweep). docs/OPERATOR_PRIVACY_CHECKLIST.md maps the controls to PIPEDA and provincial education-records law (Canada) and FERPA / COPPA (US) as a starting checklist — it is not legal advice; have your own privacy officer or counsel confirm it against your jurisdiction and any purchase-agreement obligations.

20. Extending or customizing the codebase safely

Only for an organization with source access and its own developers — skip it otherwise.

  • The hotfix overlay (§10) is for emergencies, not customization. It shadows one file at a time without a rebuild — right for "this is broken now and can't wait", wrong for "we want Campus to also do X". A hotfix still active a month later means the real fix hasn't shipped; core.W001 keeps surfacing that.
  • A permanent change means: edit source, run every gate in the release checklist (§4), rebuild, and deploy through the normal update path (§17). Every issue in §14 was caught by a gate being run properly, or shipped because one wasn't.
  • Track customizations against upstream deliberately. If Dunware keeps shipping updates to the codebase you've modified, expect merge conflicts wherever both sides touch a file; a private branch periodically rebased onto new releases is the realistic approach, not a promise that updates apply cleanly over custom changes.
  • Follow the existing patterns. PII fields use the encrypted field types, sensitive models extend SensitiveModel for audited reads, and every new viewset gets an explicit permission class. docs/DATA_MODEL.md and docs/PII_SECURITY.md are the reference.

21. Data ownership, export & portability

Every byte of real data — the database, every uploaded document, every backup — lives on hardware the organization owns or controls, from the first install. Buying outright doesn't change that; it makes direct access beyond the console unambiguously yours:

  • Direct database access — the bundled pgsql\bin\psql.exe connects with ordinary PostgreSQL tooling, and a full pg_dump gives a portable, standard-format copy independent of Campus's own backup format.
  • Structured exports — manage export_student <id> gives one family's complete record (the same tool used to fulfil a data-subject access request).
  • No proprietary lock-in — Django, PostgreSQL and Next.js are mainstream and non-proprietary. A competent team unfamiliar with Campus can read the schema, query the database and extract from it without Dunware.
